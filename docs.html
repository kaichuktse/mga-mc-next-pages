Technical summary

MGA Entertainment: Technical Summary

Klaviyo to Marketing Cloud Next and Data 360 for MGA Shop, Bratz and Little Tikes · 2026-10-14 · Reduced scope · Audience: architects and delivery leads · Draft for review

At a Glance

  • Current state: three Klaviyo accounts, one per Shopify storefront, with no shared customer view, separate opt-ins, and app data in Snapser that marketing can't reach.
  • Target: one Marketing Cloud Next org on one Data 360 data space, with a single parent profile across three stores and the apps.
  • Value drivers: cross-brand customer visibility, one opt-in across the brand umbrella, and cross-sell across brands, within brands, and between physical toys and digital apps.
  • Biggest risk: the Shopify Connector is in beta. The real-time abandonment flows depend on MGA's web team deploying the Interactions SDK during the holiday code freeze.
  • First step: a 3-week Phase 0 design phase to settle four open design decisions, identity rules and partner file specifications, submit SMS short-code registration, and get MGA's marketing users through self-paced platform learning.

Overview

MGA is consolidating three brand-level Klaviyo accounts into one Marketing Cloud Next org, so it can recognize one parent across MGA Shop, Bratz.com, LittleTikes.com and the Snapser apps. Salesforce builds 8 of the 39 Klaviyo flows: abandoned cart for each brand, a welcome drip for each brand, and two loyalty program welcome emails. MGA builds the other 31 on the platform and data Salesforce delivers, with enablement from Salesforce. The build also adds a consent model that meets both COPPA and GDPR, ingests Shopify and partner data into Data 360, and migrates Klaviyo and Yotpo data once. MGA's target go-live is March 1, 2027. Klaviyo can run month to month if launch moves past that date.

Scope

Seventeen epics in four groups:

Group Epics
Data foundation and integration E01 Data 360 foundation and unified profile · E02 Shopify commerce integration · E03 Partner file integrations (Snapser, Yotpo, Bazaarvoice, ERP) · E04 Klaviyo contacts, suppressions and Yotpo migration
Consent and channels E05 Consent, preference center and privacy · E17 Klaviyo consent import · E06 Email deliverability · E16 SMS short-code registration · E10 Brand templates
Engagement E07 Abandoned-cart flows (3) · E08 Welcome flows (3) · E09 Loyalty program welcome (2) · E11 Segmentation and activation · E12 Agentforce for Marketing · E18 MGA flow-build enablement
Go-live E14 Testing and cutover · E15 Two weeks of hypercare and configuration knowledge transfer

There is no separate training epic. MGA's users take self-paced learning in Phase 0, E18 enables MGA's flow builders in Phase 3, and Salesforce hands over the configuration in E15.

Out of scope: building, testing and cutting over the 31 MGA-built flows and their insights and audiences; the Little Tikes age-band tagging automations; Klaviyo engagement history; building ad-hoc and launch campaigns (MGA's marketing team builds these on delivered templates and segments); a move to TYB for loyalty; Circana; lawful-transfer paperwork for EU data.

MGA owns: change management and experience design; all copy and imagery (delivery recreates the current Klaviyo layouts); storefront sign-up forms in Shopify; SDK deployment on the storefronts; the Azure landing zone and the vendor file drops into it.

Solution Highlights

Org model. One business unit and one data space, with the business-unit feature off. In Marketing Cloud Next each business unit maps one-to-one to a walled-off data space, so per-brand units would block the cross-brand profile and the shared opt-in. Brands are separated by sender profile, sending domain, SMS short code, master templates, subscription and a brand attribute. MGA accepts no data isolation between brands and one shared sending-IP reputation.

Identity. The default Data 360 ruleset (normalized email, device to known), plus match rules on the Shopify customer ID and Snapser app ID so that app-only and SMS-only parents join the profile. The ruleset is built in Phase 1 and turned on once all data is imported at the end of Phase 2, so matching is tuned on real data. Children are never contacts. A child's age band and birthday sit on the parent's profile, which is the data MGA needs for its own age-band tagging.

Integration. All native connectors, with no middleware: - Shopify Connector, one connection per store, for customers, orders, history, catalog and inventory. Shopify is the catalog master. - Interactions SDK on the three storefronts for real-time browse, cart and checkout events. These SDK events are the only source for the abandonment triggers, which prevents duplicate sends from the connector's batch abandonment data. - Azure Blob Storage connector for scheduled files from Snapser (parental-consent records only), Yotpo, Bazaarvoice and a named list of ERP fields. - Native activations: six paid-media audiences (TikTok and Instagram per brand), plus engagement and unsubscribe data to Azure.

Consent. Six brand-level subscriptions (three brands × email and SMS). The umbrella sign-up subscribes a parent to all three, and the preference center offers per-brand control and an unsubscribe-from-all. Every triggered flow runs the send-time consent check except loyalty redemption confirmation; all SMS is checked. The Consent Audit Trail records GDPR evidence, and Privacy Requests handle erasure and access across the org and Data 360.

Migration load order. Contacts first (E04), then Klaviyo consent (E17), then Shopify consent going forward. The consent import doesn't create contacts and skips rows older than the stored value, so loading Shopify first would override Klaviyo consent. Each consent file covers one channel, subscription and status, so files multiply by brand and channel.

Flows. Three patterns, each built once with brand variants: abandoned cart on the native commerce trigger, welcome drips event-triggered on sign-up, and loyalty program welcome on the Yotpo file data. Each flow gets its own calculated insight and entry audience. E18 gives MGA's builders one reference insight, audience and flow, a playbook and Phase 3 working sessions; Salesforce doesn't build or test MGA's flows.

Agentforce. The standard campaign-from-brief action and Einstein segment creation, configured with brand guardrails. There are no custom agents.

Environments. A Developer Pro sandbox for build and a Partial Copy sandbox for user acceptance testing, with the email blackhole on. Data 360 metadata moves to production in a DevOps Data Kit, with objects deployed before the flows that use them. Connector credentials are re-authorized after each deployment.

Implementation Approach

Planned program duration: 25 weeks, from Phase 0 through hypercare exit, including MGA review and sign-off time. The plan sits inside a benchmark-based range of 14–30 weeks. It lands after MGA's March 1, 2027 target, so Klaviyo runs month to month until cutover. Cutting flows shortened the plan by one week: the data and consent work sets the duration, and that work didn't change.

This figure is benchmark-based, derived from the AI model's training data and general delivery patterns (not Salesforce-validated) — not a commitment. Final figures are confirmed through the applicable commercial agreement.

Three epics carry the most schedule risk: - E02: a fallback from the beta connector to a custom build. - E01: unknown identity volumes. - E06: warm-up starts with the Klaviyo consent import, so it needs MGA's warm-up emails ready late in Phase 2. Until warm-up ends we recommend unsubscribe links point to Klaviyo, with Klaviyo unsubscribes loaded into Data 360 every day.

Month-to-month Klaviyo makes either an all-brand or a brand-by-brand cutover workable. MGA chooses in Phase 0.

Effort Summary

Relative complexity across the 17 epics: three large (E01, E02, E05), four medium, eight small and one extra-small, none extra-large. The heaviest work is the data foundation, the Shopify integration and consent, which is why the flow cut barely moves the calendar.

Disciplines: - Solution architecture for Marketing Cloud Next and the consent model - Technical architecture for Data 360 identity, integration and migration - Data 360 and Marketing Cloud Next configuration - Template development - Deliverability - Quality assurance across three brands and two channels - Enablement for MGA's flow builders

The team shape is a senior onshore architecture core with an offshore build and test team, plus part-time deliverability.

Solution

MGA Entertainment: Solution

Marketing Cloud Next and Data 360 for MGA Shop, Bratz and Little Tikes · 2026-10-14 · Reduced scope (Revised Scope v2) · Status: draft for solution-lead review

What we're building

MGA moves three Klaviyo accounts onto one Marketing Cloud Next org on one Data 360 data space. The result: - One profile for each parent across the three Shopify stores and the Snapser apps. - One sign-up that subscribes a parent to all brands, with brand-level preferences and an unsubscribe-from-all. - 8 Salesforce-built flows (25 email and SMS touches), built as shared patterns with brand variants: 3 abandoned-cart flows, 3 welcome drips and 2 loyalty program welcome emails, each with its own calculated insight and entry audience. - Every data source loaded for the 31 flows MGA builds itself, plus enablement so MGA's team can build them (E18).

Shopify is the commerce and catalog master. Partner systems deliver files to an Azure landing zone that MGA owns. Delivery recreates the existing email layouts, and MGA supplies all copy and imagery.

Phase 0 is a 3-week design phase (committed by the solution lead) that settles the open decisions before build. It covers: - consent and subscription design - identity rules - the Shopify catalog mapping and the ERP field list - partner file specifications - flow specifications and the copy hand-off plan - Klaviyo contract and code-freeze dates - the Interactions SDK deployment owner and dates

Two things also start in Phase 0. SMS short-code registration is submitted (E16), and MGA's marketing users complete self-paced Marketing Cloud Next learning so they're ready to build the warm-up emails in E06 (needed late in Phase 2) and, later, their own flows.

The copy plan and flow specifications may finish in the first build sprint.

Architecture Foundations

Org strategy. One Marketing Cloud Next org, one Data 360 data space, business-unit feature off. - Each business unit maps one-to-one to a walled-off data space, so per-brand units would block the cross-brand profile and the shared opt-in (``). - Marketing Cloud Next runs without business units, and enabling the feature requires at least two data spaces. Leaving it off removes setup with no loss of function. - Brands are separated by: - sender profile - sending domain - SMS short code - master templates - Communication Subscription - a brand attribute on profile and engagement data - Trade-offs MGA accepts with this design: - no data isolation between brands - one shared sending-IP reputation (see Channels)

Access model. Use the standard Marketing Cloud Admin and Marketing Cloud Manager permission sets, layered by MGA job function. Viewing consent on records and in Data 360 depends on these permission sets. Defining marketer roles and user counts is an open question (brief Q20). There's no record-sharing design to build: this is a marketing org with no sales or service users.

Environments. - Sandboxes. A Developer Pro sandbox for build and integration testing, and a Partial Copy sandbox for user acceptance testing and segment checks against sampled production data. - Marketing Cloud Next supports all sandbox types. - Data 360 has to be turned on in each sandbox, and its connectors set up there. - The sandbox email blackhole stays on, with up to five allowed test domains. - Promotion. Data 360 metadata (data streams, data lake objects, calculated insights, data graphs) moves sandbox-to-production in a DevOps Data Kit. - The kit deploys only to a data space with the same prefix. - Connector credentials don't travel, so every Shopify, Azure and paid-media connection is re-authorized after deployment. - Marketing Cloud Next assets move with Salesforce Platform DevOps tools, with Data 360 objects deployed before the flows and content that reference them. - Source control. Use Salesforce CLI with a Git repository, since the build spans several workstreams and Data Kit retrieval is CLI-based.

Governance. MGA owns change management, governance and the operating model after go-live (decision log, 2026-10-13). Delivery hands over runbooks and naming conventions in the configuration knowledge transfer at the end of hypercare (E15). There is no delivery-run training epic: MGA's users take self-paced learning in Phase 0.

Integration posture. There is no middleware: - Shopify comes in through the native Data 360 Shopify Connector. - Partner systems come in as files through the native Azure Blob Storage connector. - Storefront behavior comes in through the Interactions SDK. - Outbound data goes through native Data 360 activation targets.

That is all native connectors. The integration risk is in the inputs MGA and its vendors supply, which the build doesn't control.

Solution by Business Process

1. Data 360 Foundation & Unified Profile (E01)

Business context. Today each Klaviyo account sees one brand. MGA can't see that a Little Tikes buyer also plays Miniverse, or that the same parent shops on Bratz.com.

Solution approach. - One data model in Data 360 for profiles, orders, catalog, consent, loyalty and app data. - An identity resolution ruleset that resolves a parent across stores and apps. - A profile data graph for personalization. - A calculated-insight framework that the flows and segments share.

Supporting architecture. - Identity. Start from the default ruleset (normalized email, device to known), then add Party Identification match rules on the Shopify customer ID and Snapser app ID. - Without those rules, an app-only parent or an SMS-only subscriber never joins the cross-brand profile. - Phone matching needs E.164 numbers on Contact Point Phone. - Keep one active ruleset, since each ruleset consumes credits. - Timing. Build and test the ruleset on sample data in Phase 1 with automatic runs off, then turn it on once every source is imported at the end of Phase 2 (Shopify, partner files, Klaviyo contacts and consent). A ruleset's automatic runs can be disabled and the run kicked off manually. Unifying on partial data would mean re-tuning thresholds and re-checking segments once the rest lands; turning it on once the data is complete means one full run, threshold tuning with MGA on real data, then the daily schedule. - The threshold for shared family email addresses is a business call tested on sample data in Phase 0 (G0101, G0102). - COPPA. Children are never contacts (``). A child's age band and birthday are attributes on the parent's profile, which is the data MGA needs if it rebuilds the 4 Little Tikes age-band tagging automations; those automations are out of Salesforce scope. - Data graphs. A profile graph on the unified individual is required for dynamic content and recommendations. A lookup graph serves the Shopify catalog to product blocks (E10). - Calculated insights. Salesforce builds the 8 insights for its own flows (one per flow). MGA builds the insights for its 31 flows, starting from the E18 reference build.

2. Shopify Commerce Integration (E02)

Business context. Shopify runs the three storefronts and holds customers, orders and the product catalog.

Solution approach. - Connector. The Data 360 Shopify Connector (beta, batch), with one connection per store. It brings in customers with consent fields, orders, order history, products, variants, prices, images, URLs and inventory. - SDK. The Salesforce Interactions SDK on the three storefronts captures browse, cart and checkout events in real time. - Order confirmation. Stays in Shopify's native notifications.

Supporting architecture. - Catalog master. Shopify is the source for product content, price and inventory (decision log). Product and variant IDs are the keys for: - email product blocks - price-drop, back-in-stock and low-inventory triggers - the catalog graph

MGA Shop sells Bratz and Little Tikes products too, so each product carries its storefront and brand. - Abandonment source: the SDK only. The native triggers read cart-level and product-level engagement objects mapped from a commerce source. - We map only the SDK's cart and checkout events to those objects. The connector's batch abandonment objects are ingested for reporting and aren't mapped to the triggers. This prevents double sends from two sources feeding one trigger (G0207, G0703). - Standard Cart, Catalog and Order interaction models cover the events. Custom SDK events are a last resort, because their schema can't change once deployed. - Beta risk. The connector is beta, enabled in Feature Manager and covered by the Beta Services Terms. - The fallback is a custom Ingestion API build. - MGA's legal and IT teams need to set a go/no-go date for the fallback (G0201). - Dependency. MGA's web team or agency deploys the SDK on three themes. Abandonment flows can't be tested until it's live (G0207), which puts storefront release dates on the critical path during the holiday code freeze.

3. Partner & Enterprise Data Integrations (E03)

Business context. Four systems hold data the flows and segments need: - Snapser: app identity and parental consent - Yotpo: loyalty balances and events - Bazaarvoice: reviews - the ERP: supplementary product fields

Solution approach. Explicit assumption (G0306): MGA or each vendor lands scheduled files in an Azure Blob Storage container that MGA owns, and Data 360 ingests them through the native connector. Delivery: - defines the file specifications - maps and ingests the files - reconciles the loads

Delivery doesn't build or host vendor extract jobs.

Supporting architecture. - Data streams. File-based streams run in Upsert mode, with deletes handled by a delete file. Azure Blob streams run on a 5-, 15- or 30-minute schedule. - Container setup. MGA's IT team provides a private container, a container-scoped access token (SAS) and the IP allowlist. Source and target use separate container paths. - Snapser. Ingest only records with parental consent (``). Linking an app user to a storefront parent depends on the identifier Snapser shares (brief Q17, G0101). - ERP. A named list of fields Shopify doesn't hold. Anything beyond that list is a change order (G0303). - Out until defined. Azure warehouse data beyond the landing files, and the Amazon feed (G0001, G0002).

4. Klaviyo & Yotpo Data Migration (E04)

Business context. About three Klaviyo accounts' worth of subscribers and suppressions, plus Yotpo members, have to arrive intact. Opt-outs must be honored from day one.

Solution approach. - A one-time, reconciled load into Data 360 and Marketing Cloud Next of Klaviyo contacts and contact points, suppressions, and a Yotpo member snapshot. It starts once E01 is done. - Klaviyo consent is a separate epic (E17), because it can only load after the subscriptions exist (E05). - Klaviyo engagement history isn't migrated.

Supporting architecture. - Contacts first. Create contacts and contact points for every Klaviyo subscriber not already in Shopify. Consent import doesn't create contacts, so this has to land before E17. - Missing consent. A record with no consent value is treated as opted out. - Suppressions. Import hard bounces and complaints so they're never mailed, and before E17's first load starts warm-up in E06. How Marketing Cloud Next holds a bulk bounce or complaint suppression list isn't confirmed in the sources checked (G0402, 🔴). - Size. S, rising to M if the suppression pattern (G0402) needs a custom build.

4a. Klaviyo Consent Import (E17)

Business context. "Klaviyo wins" on consent at cutover: a parent's existing opt-ins and opt-outs carry over exactly.

Solution approach. Import Klaviyo consent by channel into the brand subscriptions built in E05, after the E04 contacts exist, in three steps (``): 1. Engaged group first. The first load is the engaged group, so E06 warm-up can start on it. 2. Daily delta. Klaviyo unsubscribes load every day while warm-up runs (G0610). 3. Full refresh. When warm-up is complete, one full Klaviyo consent refresh loads. An opt-out recorded in either system wins, so the refresh never re-subscribes someone who opted out in MC Next.

Each load is reconciled; a final delta runs in E14 at cutover.

Supporting architecture. - Load order is load-bearing (G0407): E04 contacts, then E17 Klaviyo consent, then Shopify consent mapping going forward. The import skips any row whose consent date is older than the one stored, so loading Shopify first would quietly defeat the "Klaviyo wins" rule (G0404). - File count. Each consent import covers one channel, one subscription and one status, so the files multiply: per brand, per channel, per status, with an SMS sender code on each SMS file. - EU evidence. EU subscribers without a consent source and timestamp go to a re-permission campaign instead of a straight import (G0403).

5. Consent, Preference Center & Privacy (E05)

Business context. MGA wants one opt-in across the brand umbrella, under both COPPA and GDPR.

Solution approach. - Six Communication Subscriptions: three brands, each with email and SMS. - The umbrella sign-up writes all three brand subscriptions at once. - The preference center lets a parent manage each brand or unsubscribe from all. - After cutover, the preference center is the source of truth.

Supporting architecture. - Consent check. Consent is held per contact point and checked at send time, one subscription per send. Brand-level subscriptions let every flow check exactly one. - Which flows check. The check is on for every triggered flow except loyalty redemption confirmation (privacy team to confirm, G0503). All SMS is checked regardless. - Preference pages. Configured to MGA's design. - GDPR evidence. The Consent Audit Trail in Data 360 records consent changes. - Erasure and access. Privacy Requests cover the org and Data 360. Purging Shopify, Yotpo and Snapser so erased people aren't re-ingested is MGA's process. - Open (🔴, G0504). How a new Shopify checkout opt-in becomes subscription consent after cutover, and whether a Marketing Cloud Next unsubscribe is written back to Shopify. No source shows connector-sourced consent mapping to subscription consent on its own. Phase 0 designs the rule: accept a Shopify opt-in only when it's newer.

6. Email Deliverability (E06)

Business context. 26.7 million emails a year across three brands, from new sending domains.

Solution approach. - A sender profile and authenticated sending domain per brand. - A warm-up plan for each domain, run on emails MGA's marketing users build (they prepare through self-paced learning in Phase 0). - Sender profiles and domain authentication are set up in Phase 2. Warm-up starts with E17's first load (the engaged group) at the end of Phase 2 and runs into Phase 3 (``). Warm-up starts with the most engaged recipients. It is paced by the mailbox providers and takes six weeks in every delivery lane; AI tooling doesn't shorten it. - Unsubscribes during warm-up. We recommend Klaviyo stays the main record of unsubscribes until warm-up ends: the unsubscribe link in the body of warm-up emails points to the brand's Klaviyo page (G0609). Gmail and Yahoo also show their own one-click unsubscribe, which MC Next processes, and they expect unsubscribes handled within two days, so Klaviyo unsubscribes load into Data 360 every day (G0610). - E07–E09 can't finish before warm-up does.

Supporting architecture. - IPs. At about 2.2 million emails a month, MGA is below the volume that triggers automatic dedicated IPs. Early dedicated IPs go through the Account Executive. - Shared reputation. IPs are assigned at the org level and route by message purpose (promotional or transactional), not by brand. MGA accepts one shared sending reputation across brands (G0602), or `` reopens. - Suppression hygiene. Imported hard bounces and complaints protect the new domains during warm-up.

6a. SMS Short-Code Registration (E16)

Business context. About 300,000 SMS a year across three brands, each on its own short code.

Solution approach. Register three short codes with standard keywords. Submitted in Phase 0 and run as a parallel track. Registration goes through the carriers; the plan holds 12 weeks for approval in every lane (solution lead input), and approval has to land before E07–E09 start, since every SMS touch in those flows needs an approved code. Size XS: the work is the paperwork; the calendar belongs to the carriers.

7. Brand Templates & Content Foundation (E10)

Business context. Every flow touch, and MGA's own launch campaigns, need on-brand templates.

Solution approach. - Master email and SMS templates per brand, recreating the current Klaviyo layouts with no redesign. - Shared content blocks. - Product blocks driven by the Shopify catalog.

Supporting architecture. - Data sources. Templates bind to the profile data graph. Product blocks use repeaters on the catalog lookup graph. - Event-triggered content. These templates carry a single event data source, which can't be swapped after publish, so each event-triggered flow's template is built for its trigger. - Client dependency. MGA supplies all copy and imagery by agreed hand-off dates per flow wave. Late copy stops flow build and QA (G1002).

8. Welcome Flows (E08)

Business context. Three welcome drip series, one per brand (MGA Shop, Bratz, Little Tikes), about 6 email and SMS touches each (18 touches).

Solution approach. - Welcome series are Automation Event-Triggered Flows on sign-up, each with its own calculated insight and entry audience. - One pattern, built once with brand variants.

Out of Salesforce scope (MGA-built). MGA Shop post-purchase (new and returning customers) and win-back, and the 4 Little Tikes age-band tagging automations.

Supporting architecture. Standard configuration on the E01 foundation.

9. Behavioral & Commerce-Triggered Flows (E07)

Business context. Three abandoned-cart flows, one per brand: MGA Shop (email and SMS), Bratz (email and SMS) and Little Tikes (SMS only). Five touches in all.

Solution approach. One pattern on the native Marketing Cloud Next abandoned-cart trigger, with brand variants, each with its own calculated insight and entry audience. Trigger event data drives personalization and branch conditions.

Out of Salesforce scope (MGA-built). Abandoned checkout, browse and site abandonment, price drop, back-in-stock and low inventory. They run on the same Data 360 data Salesforce loads. The back-in-stock pattern question (G0706) moves to MGA's flow build.

Supporting architecture. - Timing. Abandonment triggers set an inactivity window (10 minutes to 7 days) and a job frequency. Event-triggered flows run about 15 minutes after the event. Per-flow delays get set in Phase 0 (G0702). - Audience reach. Only shoppers tied to a known email or phone get messages (G0704). Real-time cart events need the Interactions SDK on the storefronts (E02, G1402).

10. Loyalty Flows (E09)

Business context. Two Yotpo-driven loyalty program welcome emails, for MGA Shop and Little Tikes.

Solution approach. Automation Event-Triggered Flows on the Yotpo enrollment data in E03, each with its own calculated insight and entry audience.

Out of Salesforce scope (MGA-built). The other 9 loyalty flows: birthday, rewards and monthly reminders, redemption confirmation, refer-a-friend and anniversary. They run on the Yotpo data Salesforce loads.

Supporting architecture. - Latency. Welcome reaches the member after the Yotpo file drop, the 5-to-30-minute stream interval and about 15 minutes of flow latency (G0907). - Program structure. Whether MGA Shop and Little Tikes share one Yotpo program changes the data model (G0905). - Yotpo's own emails. Any loyalty emails Yotpo sends today are switched off at cutover (G0902). - Platform change. A move to TYB is a change order (G0906).

11. Segmentation, Activation & Data Out (E11)

Business context. MGA wants three kinds of cross-sell: - across brands - within a brand - between physical toys and digital apps

It also wants paid-media audiences on TikTok and Instagram.

Solution approach. - Segments. Reusable cross-sell segments on the unified profile. - Paid media. Six activations (TikTok and Instagram for each brand). - Exports. Engagement and unsubscribe data to the Azure target. Bazaarvoice outbound for review requests (assumed).

Supporting architecture. - Paid-media consent (🔴, G1102). Every activated segment carries an advertising-consent rule and a rule that excludes child records and child-directed audiences. Whether advertising consent piggybacks on the email or SMS opt-in, or is its own purpose, is MGA privacy's call. No source grounds the choice. Architecture decision records

0001 — All brands run in one Marketing Cloud Next business unit on one Data 360 data space

Date: 2026-10-13 · Status: accepted · Source: client-supplied

Context

MGA Entertainment runs three Shopify direct-to-consumer storefronts (MGA Shop, Bratz, Little Tikes) and today runs a separate Klaviyo account for each. Their main goals for the move are cross-brand customer visibility, one opt-in across all brands, central management of unsubscribes and preferences, and cross-sell between brands (Little Tikes to Baby Born, for example) and between physical and digital products (toy buyers and Snapser app users).

In Marketing Cloud Next, each business unit maps one-to-one to a Data 360 data space. Data spaces are walled off: data, content, campaigns and access controls can't be shared between them, and a campaign can only use segments and content from its own business unit. Marketing Cloud Next can also run with no business units at all. Separate business units per brand would therefore block cross-brand segmentation, a shared opt-in, and cross-brand cross-sell.

Decision

All brands share one Salesforce org, one Marketing Cloud Next business unit, and one Data 360 data space. Brands are told apart inside that partition by sender profile, sending domain, SMS short code, content and templates, and brand attributes on the unified profile and in segments. They are not separate partitions.

Consequences

  • Identity resolution produces one Unified Individual per person across all three storefronts and the Snapser apps, so cross-brand and physical/digital cross-sell is possible.
  • One consent model: a shared umbrella opt-in plus brand-level subscriptions, managed in one preference center.
  • Flow patterns that repeat across brands (abandoned cart, browse abandonment, back-in-stock, welcome, loyalty) can be built once as shared patterns with brand-specific versions, not once per brand.
  • No data separation between brands. If brand-level user access or data isolation is needed later (an acquired brand, a regional or regulatory split such as EU recipients), it needs another business unit and data space, and assets in this unit can't be moved there (a campaign's business unit can't be changed after it's created).
  • Brand-level reporting and message-credit tracking come from brand attributes and filters, not per-business-unit consumption views.

Grounds

  • Customer answer, "Questions for MGA Entertainment" (10/13/26), Business unit organization row: "Assume 1 combined org for all brands"; cross-brand visibility, single opt-in, and cross-sell requirements in the same row.
  • User direction, 2026-10-13: "Assume one business unit and one Data 360 data space for all brands combined."
  • Marketing Cloud Next business units built on data spaces (1:1, walled off, optional).
  • Business units in Marketing Cloud Next: data partitioning and governance (assignments can't be changed afterward).

0002 — COPPA and GDPR both apply; all data is hosted in the US

Date: 2026-10-13 · Status: accepted (US hosting is an assumption pending customer confirmation) · Source: client-supplied

Context

MGA markets kids' brands (Little Tikes, Bratz, Baby Born, Miniverse) and today tags Little Tikes customers by child age (0–12 months through 5+ years). The Snapser apps hold parent-consent data. The customer has confirmed that US children's privacy rules (COPPA) and EU data protection rules (GDPR) both apply, so EU recipients are in the audience. The customer has not stated any data residency requirement.

Decision

  1. COPPA. The marketing contact is always the parent or adult. Children are never addressable contacts in Marketing Cloud Next. Child age or birthday is stored only as an attribute of the parent's profile, used for age-band segmentation. Snapser app data comes in only for records with parental consent.
  2. GDPR. EU recipients get explicit, provable consent per channel (captured with source and timestamp), a working preference center and unsubscribe, and handling for data-subject requests (access, erasure) across the Salesforce org and Data 360.
  3. Hosting. All brands and regions, EU included, live in the single US-hosted org and data space set by ``. There's no regional partition.

Consequences

  • The consent model, preference center, and migrated Klaviyo consent must carry evidence of how and when consent was given. Migrated EU subscribers without provable consent may need re-permissioning, not a straight import.
  • Erasure and access requests must reach Data 360 as well as the org. Salesforce Privacy Center does this but is a separately licensed add-on. Without it, the process is manual or needs another tool.
  • Lawful transfer of EU personal data to the US (data processing agreement, transfer mechanism) is a customer and legal responsibility, not delivery scope.
  • If the customer later requires EU data to stay in the EU, this decision and `` both reopen: likely a second org or data space, which is a major change order.

Grounds

  • "Customer provided Flows" (10/13/26): Little Tikes "Customer Segmentation – Ages 0–12 Months … 5+ Years" automated tagging flows.

  • Marketing Cloud Next consent model: consent is held per contact point and checked at send time.

0003 — Domain warm-up starts with the Klaviyo consent import; Klaviyo holds unsubscribes until warm-up ends

Date: 2026-10-15 · Status: accepted (the per-subscriber Klaviyo link is an assumption to confirm, G0609) · Source: Solution Lead direction

Context

Domain warm-up for MGA's 3 sending domains (E06) takes about six weeks, paced by the mailbox providers. Until now it started after consent was complete and ran in the first six weeks of Phase 3, so in the AI-native lane it set the Phase 3 floor. Warm-up can't start on an empty audience: Marketing Cloud Next treats a contact point with no consent value as opted out, and hard bounces and complaints must be suppressed before a new domain sends. Klaviyo keeps sending through the holiday peak and stays live until cutover, so during warm-up subscribers exist in both systems.

Decision

  1. Warm-up starts with E17. Domain authentication and sender profiles are set up in Phase 2. Warm-up starts as soon as E17's first load (the engaged group, with suppressions already loaded by E04) is in, at the end of Phase 2, and runs into Phase 3.
  2. Body unsubscribe links point to Klaviyo during warm-up. We recommend MGA keep Klaviyo as the main record of unsubscribes until warm-up ends: the unsubscribe link in the body of MC Next warm-up emails goes to the brand's Klaviyo unsubscribe page.
  3. A daily delta, not only a final load. Gmail and Yahoo show their own one-click unsubscribe, which MC Next processes itself, and they expect unsubscribes processed within two days. So Klaviyo unsubscribes are loaded into Data 360 every day for the whole warm-up.
  4. One full refresh after warm-up, opt-out wins. When warm-up is complete, one full Klaviyo consent refresh loads into Data 360. An opt-out recorded in either system wins, so the refresh never re-subscribes someone who opted out in MC Next.

Consequences

  • E06 moves to Phase 2 in the roadmap (setup and warm-up start); E07–E09 still can't finish before warm-up does.
  • E17 now loads in three steps (engaged group, daily delta, full refresh). It stays size S.
  • Traditional holds at 25 weeks (3/4/7/7/2/2); Phase 3 is set by build effort, so warm-up becomes buffer. Augmented holds at 23 weeks. AI-native goes from 22 to 21 weeks (3/3/6/5/2/2), 4,250 PS hours, because warm-up no longer sets its Phase 3 floor. SMS approval at week 12 still holds Phase 3 start at week 13 in every lane.
  • New dependency on MGA: warm-up emails built by the time E17's first load lands (G0608).
  • New risks: the per-subscriber Klaviyo link (G0609) and a missed daily delta (G0610).

Grounds

  • Solution Lead direction, 2026-10-15: run warm-up emails at the same time as E17; point unsubscribe links to Klaviyo; one Klaviyo consent update into Data 360 after warm-up. Adjusted (agreed the same day) to add the daily delta and the opt-out-wins rule.
  • Records with no consent value are treated as opted out.
  • Hard bounces and complaints damage sender reputation; complaints of 0.1% can cause blocking.
  • Warm-up starts with the most engaged recipients.
  • Internal Salesforce engineering notes (Marketing Cloud one-click unsubscribe header; Gmail and Yahoo bulk-sender requirements): inbox one-click unsubscribes are processed by the sending platform, with a two-day processing expectation.
